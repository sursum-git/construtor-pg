Instrucao para agentes de IA

Padrao Kendo de grids e formularios

Guia para adaptar telas existentes em um projeto Kendo UI + PHP + Symfony + API Platform ao mesmo padrao visual e comportamental usado no motor CRUD dinamico deste projeto.

Escopo Grids, filtros, formularios, acoes, mensagens e comportamento mobile.
Nesta etapa Nao converter para motor JSON. Apenas padronizar as telas existentes.
Referencia Usar Kendo UI local, cultura pt-BR, tema neutro com azul discreto.

1. Prompt base para colar no outro projeto

Voce esta trabalhando em um projeto PHP/Symfony/API Platform com frontend em Kendo UI.
Sua tarefa e padronizar grids, filtros e formularios existentes para o mesmo comportamento descrito neste documento.

Regras principais:
- Nao reescreva a tela inteira sem necessidade.
- Nao migre ainda para motor JSON/metadados.
- Preserve controllers, rotas, entidades, DTOs e endpoints existentes.
- Use componentes Kendo UI nativos sempre que possivel.
- Use cultura e mensagens pt-BR.
- Aplique o padrao visual neutro com azul discreto.
- Substitua alerts/confirms nativos do browser por mensagens ou janelas Kendo.
- Garanta comportamento mobile first.
- Nao use eval, template livre vindo do backend ou injecao arbitraria de HTML.
- Antes de finalizar, teste desktop e mobile.

2. Padrao geral de tela

  • A tela deve abrir diretamente na experiencia util, sem landing page ou explicacao decorativa.
  • O cabeçalho no desktop deve ocupar uma linha sempre que houver espaco suficiente.
  • O fundo deve ser neutro; o azul deve aparecer em titulos, links, badges, bordas leves e botoes primarios.
  • Quando houver tema escuro, ele deve alterar fundo, superficie, texto, bordas, botoes, inputs, grids e filtros aplicados.
  • Data/hora da ultima atualizacao deve aparecer em badge compacto, sem texto longo como "Atualizado em".
  • Ajuda, logs e tema devem usar botoes compactos com icones e tooltip.
  • Versao do programa so aparece se existir configuracao correspondente.
  • Ajuda e logs so aparecem se existirem conteudo, path, URL ou endpoint configurado.

3. Padrao de grid

3.1 Estrutura

  • Usar Kendo Grid real, nao tabela HTML simples.
  • Habilitar, quando aplicavel: paginacao, ordenacao, filtro nativo, redimensionamento, reordenacao, menu de coluna e agrupamento.
  • Aplicar textos, datas, numeros e mensagens em pt-BR.
  • A coluna de acoes deve ser a primeira coluna do grid.
  • As acoes de linha devem ficar em menu compacto, semelhante ao menu das colunas.
  • O clique duplo na linha deve abrir o formulario em modo consulta, sem ativar botao de incluir, alterar ou excluir.

3.2 Appbar do grid

  • Usar botoes Kendo com icones.
  • Botoes comuns: Incluir, Filtros, Atualizar, Ordenacao, Agrupamento, Leiaute, Imprimir e Acoes em massa.
  • O botao Atualizar deve usar icone equivalente a arrow-rotate-cw.
  • O botao de acoes em massa so deve aparecer quando existirem acoes em massa cadastradas.
  • O botao Imprimir so deve aparecer quando existirem opcoes de exportacao.
  • Em mobile, os botoes do grid devem ser icon-only sempre que necessario para caber em uma linha.

3.3 Filtros aplicados

  • Quando algum filtro estiver aplicado, exibir chips/labels informando os filtros ativos.
  • Deve ser possivel desativar a exibicao dos filtros aplicados por configuracao da tela.
  • Ao clicar em um chip de filtro aplicado, abrir uma janela para alterar apenas aquele filtro e, ao aplicar, atualizar o grid inteiro.
  • Deve existir botao para limpar todos os filtros.

3.4 Leiaute, ordenacao e agrupamento

  • Leiautes, ordenacoes e agrupamentos devem abrir em janelas Kendo, nao ocupar espaco permanente na appbar.
  • Deve ser possivel salvar varios leiautes, ordenacoes e agrupamentos, com nome e opcao de padrao.
  • Congelamento de colunas deve ser opcional, claro ao usuario como recurso apenas desktop.
  • As colunas devem iniciar descongeladas, exceto quando houver leiaute salvo explicitamente dizendo o contrario.
  • O cadeado fechado deve representar coluna congelada; cadeado aberto deve representar coluna nao congelada.
  • Ao clicar no cadeado, nao pode ordenar nem mover coluna. Deve apenas alternar congelamento daquela coluna.
  • Agrupamento deve permitir selecionar campos e tambem colunas a contar ou somar.

3.5 Exportacao

  • No grid, usar exportacoes nativas do Kendo sempre que possivel: Excel, PDF e CSV.
  • O botao de impressao/exportacao so aparece se houver opcoes disponiveis.
  • Nome do arquivo deve ser coerente com a tela e filtros aplicados quando possivel.

4. Padrao de filtros

  • O filtro deve ser uma janela Kendo que pode abrir automaticamente na entrada ou apenas quando o usuario clicar no botao Filtros.
  • Quando abrir automaticamente, pode existir configuracao para esperar o usuario clicar em Filtrar antes de carregar o grid.
  • Deve existir opcao de abrir o filtro maximizado tanto na entrada quanto na abertura manual.
  • A janela de filtro deve ter appbar no rodape, fixa, com botoes alinhados a esquerda.
  • Os campos devem ficar entre appbar superior e appbar inferior, com rolagem vertical quando necessario.
  • Labels devem ficar acima dos campos.
  • Campos de filtro devem ficar um abaixo do outro, exceto operador e range, que devem ficar na mesma linha do campo.
  • Deve ser possivel dividir filtros em abas.
  • Salvar filtro deve abrir janela pedindo nome e se sera padrao; nao usar prompt/alert nativo do browser.
  • O seletor de filtros salvos deve ocupar o minimo de espaco possivel e usar "Livre" quando nao houver filtro salvo selecionado.

4.1 Tipos de filtro

Tipo Comportamento esperado
Texto Igual, inicia com, contem, nao contem, vazio, nulo, nao vazio, nao nulo, entre valores e lista separada por virgula.
Numero/decimal Igual, maior, maior igual, menor, menor igual, range, esta contido em e nao esta contido em.
Data DatePicker, DateRangePicker e data relativa: ontem, hoje, amanha, quantidade de dias, semanas, quinzenas, meses ou anos, com Antes/Depois.
Data/hora DateTimePicker ou equivalente Kendo.
Logico Sim, Nao e Todos.
Chave estrangeira DropDownList, janela de busca, DropDownTree, checkbox ou checkbox group, conforme a necessidade.

5. Padrao de formulario

5.1 Janela e appbars

  • Formulario deve abrir em janela/popup Kendo, com opcao de maximizar.
  • Deve existir propriedade/comportamento para abrir maximizado por padrao.
  • Appbar de cabecalho: Incluir, Alterar, Excluir, Logs, Imprimir e Outras acoes, conforme permissao e configuracao.
  • Appbar de rodape: Confirmar e Cancelar sempre alinhados a esquerda.
  • O comportamento de fechar ou nao a janela ao salvar/cancelar deve ser configuravel.
  • Em mobile, o formulario deve ocupar corretamente a largura, sem sobra lateral direita.

5.2 Estados dos botoes

  • Ao entrar em Alterar, os botoes Incluir e Excluir devem ficar desabilitados.
  • Ao abrir por duplo clique no grid, o formulario entra em consulta: nenhum botao de acao de cabecalho fica ativo.
  • Em consulta por duplo clique, Confirmar e Cancelar ficam desabilitados.
  • Cancelar nao deve sair da pagina. Deve desativar a acao corrente, liberar botoes do cabecalho e desativar botoes do rodape.
  • Botoes Anterior e Proximo devem ser opcionais e usar apenas icones, sem texto.

5.3 Campos e abas

  • Formulario deve suportar multiplas abas.
  • A primeira aba deve mostrar conteudo imediatamente, sem exigir clique inicial.
  • Labels devem ficar acima dos campos.
  • Deve existir suporte a campo somente leitura e campo renderizado apenas como label.
  • IDs de campos devem ser unicos: usar formId-campoId. Se o campo nao tiver id, gerar com formId-nomeDoCampo.
  • Evitar IDs previsiveis para autorizacao. ID organizado nao substitui seguranca no backend.

5.4 Eventos e recarga de dados

  • Eventos de entrada, modificacao e saida podem chamar APIs, mas nao podem executar JavaScript livre vindo do backend.
  • Ao mudar um campo, deve ser possivel enviar todos os valores do formulario ou apenas campos especificos para a API.
  • A API pode retornar efeitos seguros: alterar valor, limpar valor, habilitar, desabilitar, tornar readonly, esconder, mostrar, exigir, remover obrigatoriedade, trocar opcoes e exibir mensagem.
  • Campos dependentes devem poder recarregar opcoes. Exemplo: ao alterar UF, recarregar Cidade usando o valor da UF como parametro.
  • Regra de negocio deve ficar no backend. O frontend apenas aplica o resultado seguro retornado pela API.

5.5 Situacao e etapas

  • Quando existir campo de situacao, exibir logo abaixo da appbar de cabecalho.
  • Exibir label pequeno acima do componente de situacao.
  • Se houver muitos passos, priorizar o passo atual e permitir rolagem horizontal.
  • Ao clicar em cada fase, abrir historico com data/hora e usuario que fez a alteracao.
  • Formulario por etapas deve permitir definir etapas, campos por etapa, obrigatorios para avancar e permissoes por etapa.
  • Cada etapa pode ter botao de log proprio, sem conflitar com rolagem vertical.

6. Mobile

  • Mobile first: nao deixar appbars com botoes quebrando de forma desorganizada.
  • No grid mobile, deve haver duas possibilidades: manter grid com colunas reduzidas ou usar card/template seguro.
  • Template mobile nao deve aceitar HTML livre do backend. O backend pode escolher um template conhecido e informar quais campos vao em cada area.
  • No card mobile, acoes como Incluir, Alterar, Excluir e Outras acoes podem aparecer no card; no formulario mobile, manter Confirmar, Cancelar e Navegacao.
  • Botoes de grid no mobile devem usar apenas icones quando necessario para caber em uma linha.
  • Data/hora, log e ajuda no cabecalho mobile devem ficar alinhados, sem embolar.

7. Mensagens, janelas e acessibilidade

  • Substituir alert, confirm e prompt nativos por Kendo Notification, Kendo Window ou Kendo Dialog.
  • Mensagens devem ter contraste neutro e nao misturar fundo verde forte com azul forte.
  • Evitar mensagens sobrepostas; esconder notificacao anterior antes de mostrar nova, quando fizer sentido.
  • Botoes icon-only precisam de title e aria-label.
  • Janelas devem ter botoes de confirmacao/cancelamento alinhados a esquerda.
  • Janelas de ajuda/novidades devem ficar acima da janela de filtro quando ambas existirem.

8. Seguranca e integracao com backend

Regra de seguranca Nunca confiar no frontend para permissao, visibilidade, validacao critica, tenant, usuario ou autorizacao. O backend Symfony/API Platform deve validar tudo novamente.
  • Permissoes visuais no frontend servem apenas para experiencia do usuario.
  • Endpoints devem validar usuario, perfil, tenant, registro e transicao de estado.
  • Nao permitir que retorno da API injete script ou HTML arbitrario.
  • Templates permitidos devem ser uma lista fechada no frontend.
  • Eventos de formulario devem aceitar apenas acoes seguras conhecidas.
  • Logs e historicos devem vir do backend, nao do estado local do browser.

9. Checklist de entrega por tela

  • Grid usa Kendo Grid real.
  • Cultura, mensagens, datas e numeros em pt-BR.
  • Cabecalho compacto no desktop e organizado no mobile.
  • Toolbar com icones e botoes condicionais.
  • Coluna de acoes como primeira coluna e em menu compacto.
  • Filtros em janela com rodape fixo e botoes a esquerda.
  • Filtros aplicados visiveis quando habilitado.
  • Salvar filtro/layout/ordenacao/agrupamento sem prompt nativo.
  • Formulario em janela Kendo com appbar superior e rodape fixo.
  • Estados de Incluir/Alterar/Excluir/Consulta corretos.
  • Primeira aba do formulario aparece sem clique adicional.
  • Mobile sem overflow lateral e com botoes compactos.
  • Alerts/confirms/prompts nativos removidos.
  • Permissoes e validacoes criticas confirmadas no backend.
